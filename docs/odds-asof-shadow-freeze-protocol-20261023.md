# オッズの時間順学習：as-of監査と封印シャドー予測

**2026-10-23。時刻による先読みの監査と今後の予測を封印する実装であり、新しい実競馬の的中成績や前向き予測力を示すものではない。**

## 1. 実際に分かった時刻上の問題

2026年10月12日の京都8〜12Rの単勝全頭・ワイド全組について、ソース掲載更新時刻と当方の実際の受信時刻を別々に調べた。

| レース | 全予測用価格の最終受信 | 発走予定 | この時点で同日他レースの確定着順を学習できるか |
|---|---|---|---|
| 京都8R | 13:27:02.145 JST | 14:00 | **不可能** |
| 京都9R | 13:27:09.105 JST | 14:35 | **不可能** |
| 京都10R | 13:27:17.798 JST | 15:10 | **不可能** |
| 京都11R | 13:27:25.990 JST | 15:45 | **不可能** |
| 京都12R | 13:27:33.944 JST | 16:30 | **不可能** |

最終受信の13:27:33.944から、最初のレース8R発走14:00までは**約32分26秒**。5レースとも、最初の結果が出る前に予測用の全市場資料が受信済みだった。レース番号が若いほど結果を学習に使えるという仮定は誤りで、5レースをランダムに分割したり、8Rの結果から9〜12Rの13:27時点の予測係数を後付けで決めたりすれば先読みになる。

JRA公式結果の保存ファイル data/2026-10-12/official-results-final.json には独立確認時刻が同日**23:46:27 JST**と記録される。これはJRAが結果を初めて公開した時刻ではない。現在の資料から確認できる保守的な利用可能時刻としてのみ用いる。公式結果を最初に閲覧できた時刻を推測して生成しない。

## 2. 利用可能な情報を厳密に判定するコード

[odds_asof_training_eligibility.py](../scripts/odds_asof_training_eligibility.py)が、各ターゲットの「全必要市場を受信した時刻」をas-of時点とする。ある旧レースの結果が学習候補となる条件は、

- 旧レースが発走済みであること
- 独立の公式結果確認がターゲットのas-of時刻より**厳密に前**であること
- 公式結果・ターゲット市場の出所とタイムゾーンが照合できること
- 同じレースを自身の学習に含めないこと

である。現存の実京都5レースでは**5ターゲットに対し結果→予測の適格な情報関係は0本**。合成の別日3レースでは、初日に確認済みの2結果のみが翌日のターゲットに適格となることをユニットテストで確認する。

この制約は「市場に情報がない」という生態学的・統計的な否定ではなく、**今の保存資料では当日結果を使う時系列学習の主張ができない**という測定上の結論である。

## 3. 未来レース用の予測封印・事後採点

[odds_shadow_freeze_score.py](../scripts/odds_shadow_freeze_score.py)を追加した。これは正式v3.1とは別の市場情報階層用の実験システム。

- 予測前にローカルで使用許諾を確認した全頭WIN・全ペアWIDEのJSONを作る。元データをダウンロード・再配布する機能は持たない。
- 市場価格の更新時刻、各ページ受信時刻、発走時刻を別々に照合。WINとWIDEの元更新表示時刻が一致しない場合、全馬・全ペアが揃わない場合、発走10分以内または発走後の入力を拒否する。
- 価格の公表より前に決めた2モデルの係数を要求する。ひとつは市場PLの係数0、もうひとつは前もって凍結した馬ノード・ペア残差の係数。後から良い係数に変えることを禁止する。
- 結果データには触れず、同じ共同順位確率から単勝総和1、3着以内総和3、三連複総和1の予測配列を作り、モデル係数・原データSHA256・予測時刻と合わせて**正規化JSONのSHA256で封印する**。
- 公式結果を独立に確認した後だけ別コマンドで封印を検証し、**勝馬Log lossを主要指標**、Top3 Brierを副次指標、三連複Log lossを探索指標として自動採点する。価格原データ・表示倍率の表を封印成果物へ複製しない。

### 注意：SHA256だけでは前向き予測を証明できない

自分が書いたローカルの発走前時刻とSHA256は**内容が変わったことを検出する手段**であって、そのファイルが実際に発走前に存在したという独立証拠ではない。Gitのauthor/committer日時も自分で変更できる。実際の前向き証拠には、レース開始より前に外部で受付済みのGitHub Actionsサーバ時刻や第三者タイムスタンプ等による**独立した事前存在の検証**がさらに必要。

このツールは独立の外部証明を自動確認しないため、出力は常に**未認証のローカル・シャドー予測**と表示される。いかなる状況でも、このツールから既存のv3.1正式20レース台帳に書き込まない。

## 4. 再現・運用例

完全人工の8頭・28ワイド組の未来サンプルだけを使う例：

~~~bash
python -m unittest discover -s tests -p 'test_odds_asof_training_eligibility.py' -v
python scripts/odds_asof_training_eligibility.py --output tmp/odds-asof-eligibility.json
python scripts/odds_asof_training_eligibility.py --demo --output tmp/odds-asof-synthetic-demo.json

python -m unittest discover -s tests -p 'test_odds_shadow_freeze_score.py' -v
python scripts/odds_shadow_freeze_score.py demo \
  --freeze-out tmp/synthetic-winwide-shadow-freeze.json \
  --score-out tmp/synthetic-winwide-shadow-score.json
~~~

本物の研究用データを**公開GitHubではない**権利を確認したローカル環境で管理する場合：

~~~bash
python scripts/odds_shadow_freeze_score.py freeze \
  --source private/authorized_snapshot.json \
  --output private/freeze.json

# レース後、独立の公式結果・公表時刻を確認してから
python scripts/odds_shadow_freeze_score.py score \
  --freeze private/freeze.json \
  --result private/official_top3.json \
  --output private/score.json
~~~

これらのシャドー結果は前向き性能とは別の段階に置く。研究を本当に進める条件は**独立した複数開催日の実データ**、発走前の係数固定とその第三者確認、将来の勝馬・Top3の事前主要指標による一度限りの採点である。

## 5. 後続オッズも、受信前の予測を学習する教師にはできない

着順結果だけではなく、**次時点の市場価格そのもの**についてもas-of学習可能性を監査した。レース8Rの全11頭の13:44表示単勝オッズは、別ファイル data/2026-10-12/r8_markets_latest.json で確認でき、受信時刻は**13:44:55.575221 JST**（Git blob SHA: 5e84f3c445249564b2cd7ed358591ed02a8b2d88）。

しかし京都8〜12Rの予測元の単勝＋ワイド価格は全て13:27台までに受信済みだった。したがって、京都8Rの13:44時点の価格を学習の教師にしてから**9〜12Rの13:27に戻って予測したことにする**のも先読みである。保存済みの5レースについて、実際に確認できる「後続市場の全頭価格→別レースの予測時点」の適格な時間順関係は**0本**であった。

追加した next_quote_training_graph は、公式着順が公表されたかではなく、次市場の**全頭価格が予測に必要な先行情報の受信より前に既に受信されていたか**を判定する。後続市場はレース終了前でも将来の他レース予測の教師にできる場合があるが、時計の条件を満たさない場合には拒否する。別の完全人工例では先行市場の次価格が13:01に受信済みなら、13:46時点の別レースには学習の教師として利用できることも検証した。

**区別すべき3段階**：実際の価格から事後的に分かること、予測の入力が入手できた時点で本当に学習可能だったこと、さらにその予測が発走前に独立の外部タイムスタンプで封印されていたこと。現状のリポジトリが実証しているのは最初の段階と、残りの段階を検査するソフトウェアである。


## 6. 2026-10-24：SHA事前提出の第三者受付を検証する基盤

[GitHubサーバ受付時刻による事前SHAコミットメントの新しい手順](odds-github-server-preseal-attestation-20261024.md)を追加した。ローカル予測ファイルのSHA256、競走ID、予定発走、必要市場の最終受信時刻という**4つの非機密文字列だけ**をworkflow_dispatchへ提出し、後からGitHub APIのrun.created_at、受け付けたartifactおよび最初の同一レース試行であることを照合する。ハッシュは元の単勝・Top3・三連複予測内容へ照合するが、GitHubへ元オッズや確率表は送らない。

ただし**実稼働はまだ始まっていない**。このworkflowは現時点ではDraft PRにあり、GitHub仕様によりデフォルトブランチへ導入するまでは起動できない。SHAと自己申告の時刻だけでは本当の事前予測やソースの真偽を証明しない。GitHubの受付時刻を第三者から確認できる状態になって初めて、予測内容の**事前存在**だけを裏付けられる。これは実勝率の校正・収益証明・v3.1の正式holdout登録とは異なる。
